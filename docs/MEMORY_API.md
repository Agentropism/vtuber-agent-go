# 长期记忆：存储格式与召回

记忆是**追加式 JSON Lines 文件**（`[agent].memory_file`，默认不启用）。一行一条记录，
文件只追加、不重写——删除靠墓碑标记。为什么不是 SQLite：纯 Go 无 CGo 的驱动要拖进十几个
模块，而这里真正需要的只是「记住说过的话 + 按关键词找回来」，几千条量级远没到需要索引结构。

HTTP 接口（查询 / 新增 / 删除）见 [`docs/API.md`](API.md) 的「5. 记忆读写」。

## 1. 记录格式

一条记忆：

```json
{"time":"2026-09-21T11:13:49.284Z","channel_id":"room_123456","user":"观众甲","text":"我说过喜欢草莓","reply":"记住啦","weight":1}
```

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `time` | RFC3339 | 记录时间；接口新增时留空则取当前时间 |
| `channel_id` | string | 渠道号（`room_123456` / `group_10001`） |
| `user` | string | 说话的人 |
| `text` | string | 用户说的话（召回按它打分） |
| `reply` | string | 当时怎么回的 |
| `weight` | int | 重要度：普通弹幕 1，礼物/大航海更高，SC 最高；<=0 时按 1 存 |

一条墓碑（删除标记）：

```json
{"op":"delete","id":2,"time":"0001-01-01T00:00:00Z",...}
```

`op` 为 `delete` 的行只认 `id`，其余字段忽略（序列化时会带上零值，读取时不管）。

## 2. ID 语义

**ID 就是记录在文件中的行号**（1 起）。追加式文件里行号稳定，因此：

- 接口返回的 `id` 可以直接用于删除；
- 删除不改变其他记录的 ID（墓碑也是追加的一行，占掉一个行号）；
- 手工编辑文件（删行、重排）会破坏这个对应关系——要改就整份重写并重新导入。

## 3. 删除

`Delete` 追加一条墓碑，并把该条从内存索引里摘掉（倒排索引整份重建：删除是低频操作，
O(n) 重建比增量维护更不容易出错）。

- 文件只增不减——需要真正回收空间时再加压缩步骤（重写文件 + 丢弃墓碑）；
- 墓碑留下了「什么时候删了哪条」的痕迹；
- 删除不存在的 ID 返回错误（接口层映射为 404）。

## 4. 召回打分

`Recall(query, limit)`：命中词元数 × 权重系数 ÷ 时间衰减，同分按时间倒序。

- 词元化：中日韩文本用**字符二元组**（无分词器时的常用近似），ASCII 按单词切；
- 权重系数随 `weight` 上升，时间衰减随记录变旧而下降；
- `query` 词元化后为空（例如全是标点）时返回空。

不带 `query` 的接口调用回的是**最近 N 条快照**（`Snapshot`），不经过打分。

## 5. 与上一版契约的关系

本文原来描述的是 Python 时代的独立记忆服务（`POST /api/v1/events`，按消息召回并回注文本）。
那条路径随「单二进制 Go 重写」消失：记忆现在是本进程内的 `internal/core/agent/memory`，
会话层通过 `conversation.Memory` 接口调用（适配器在装配层 `memoryAdapter`），不再有跨进程契约。
